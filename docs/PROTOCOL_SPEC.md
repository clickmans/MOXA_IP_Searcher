## 2. 协议 A：UDP 4800（主力，覆盖串口服务器/网关/部分交换机）

### 2.1 请求（8 字节，广播，✅ 实证有效）

```
01 00 00 08 00 00 00 00
```
`[0]`=0x01 命令（搜索）；`[2:4]`=0x0008 总长；其余 0。

> 官方另有 32 字节变体（8 字节头 + 12 字节本机 ID + 12 字节对端 ID），**本工具不需要**；8 字节即可拿到 IP。

### 2.2 应答（✅ 实证）

公共头 8 字节：
```
[0]      = 0x81（0x80 | 命令）
[1]      = 0x00 或 0x04（标志；0x04 的 20 字节应答不含 IP，忽略）
[2:4]    = 总长（BE16）
[4:8]    = 0
[8:20]   = 12 字节设备 ID：前 6 字节为型号/端口码，**后 6 字节 = 设备 MAC**
[20:24]  = 设备 IPv4（仅长度 ≥ 24 的应答存在）
```

实帧（NPort 5110A）：
```
8100001800000000005101801a51500b88000029c0a864fe
  len=24  id=00 51 01 80 1a 51 | 50 0b 88 00 00 29   mac=50:0B:88:00:00:29  ip=192.168.100.254
```

**解析规则**
1. `len < 24` → 丢弃（20 字节应答无 IP，无法定位）。
2. `payload[0] != 0x81` → 丢弃。
3. MAC = `payload[14:20]`，IP = `payload[20:24]`。
4. 若 `payload[2:4]` 与 `len(payload)` 不等 → 仍接受（防御式），但记录到调试日志。
5. 长度 > 24 时（如 40 字节）**尾随内容忽略**（实测为双 IP 主机的第二个 IP+MAC，如 `192.168.100.254→...:89`）。

### 2.3 型号查询（可选增强，✅ 实证）

对每个已发现设备（IP 已知）**单播**发送：
```
03 00 00 14 <seq:4B> 00 00 00 00 <deviceID 12B>
```
- `<seq>` 为 4 字节序号（BE，任意，官方用 0..N 递增）。
- `<deviceID>` = 对应应答的 `payload[8:20]`。
- 目的端口 4800，目的地址 = 设备 IP。

应答 `0x83`（✅ 实证）：
```
83000068 00000000 <ID 12B> 5400040000000100000000 "Model\tNP5110A\nUpgtouts\t80000\n..."
```
**型号解析**：在 payload 中搜索 ASCII `"Model\t"`，取其后到 `\n` 之间的字符串（实测偏移 30，但**必须用搜索而非固定偏移**，不同机型头部 10/11 字节不等）。

> **固件版本**：`0x83` 文本里**没有**固件字段（实测 MGate MB3180 仅有
> `Model / Magic / Upgtouts / SecurityView / UserAccount`）。若某些机型出现 `Firmware\t` 键则顺手取值，
> 否则留空——**不要**为此新增未验证的命令探测。
> 4000 / 5800 协议的应答同样不含固件字段。

> ⚠️ **`0x83` 的"拒绝"语义**：部分机型（实测 NPort 6450、AWK-1132C）对本命令回
> `83 04 00 14 <seq> <ID12>`——共 20 字节、`payload[1] & 0x04 != 0`、**无数据**。
> 这表示"设备不支持/不在此命令提供"，**不是错误**；型号需走名称回退（§2.5）。

### 2.4 名称与固件（✅ 2026-11-02 实机实证）

统一帧格式：`<cmd> 00 00 14 <seq:4B> <deviceID:12B>`（总长 20，长度字段 `0x14`），目的 `设备IP:4800`。

| cmd | 应答 | 数据位置 | 含义 |
|---|---|---|---|
| `0x10` | `0x90`（60 B） | `payload[20:]` 起第一个 NUL 结尾 ASCII | 设备名称，如 `MG-MB3180_0001`、`NP6450_0001` |
| `0x16` | `0x96`（36 B） | `payload[20:]` 的 16 B tail | 固件版本 + 短序列号 |
| `0x7a` | `0xfa`（40 B） | `payload[28:]` ASCII | 序列号，如 `CBFIR1000579`（本工具暂未使用） |

**`0x16` tail 布局（16 字节，✅ 四机型交叉验证）**：

| 偏移 | 含义 | 实测 |
|---|---|---|
| `[2]` | 次版本号（十进制半字节，见下） | MB3180 `0x07`→7；NPort6450 `0x10`→10；AWK-1132C `0x00`→0；AWK-1137C `0x0b`→11 |
| `[3]` | 主版本号（十进制） | 分别为 `0x02`→2、`0x01`→1、`0x01`→1、`0x01`→1 |
| `[8:10]` | 短序列号（LE uint16） | 579 / 5599（与名称后缀、MXConfig Serial 列一致） |

→ 版本 `V{major}.{minor}`：`V2.7`、`V1.10`、`V1.0`、`V1.11`（与 MXConfig `V2.7build25060913`、DSU `Ver1.10` 吻合）。

**次版本号解码规则**（`minorFromTail4800`，两个真值同时成立才算对）：

| 形态 | 规则 | 例 |
|---|---|---|
| 双位形态（高半字节 1..9） | `minor = high*10 + low`，低半字节必须 0..9 | `0x10`→10（不是 16）、`0x99`→99 |
| 单位形态（高半字节 0） | 整个低半字节即十进制值 0..15 | `0x07`→7、`0x0A`→10、`0x0b`→11 |

**`minor=0` 合法**（AWK-1132C 即 `V1.0`）；`major==0`、`major>99`、`0x1A`（双位形态低半字节越界）、
`0xA1`（无十进制高半字节）仍判无效——宁可不显示，也不猜一个版本号。

> ⚠️ **2026-11-02 修正**：早期实现把 `[2]` 写死为严格 BCD（半字节必须 ≤9），
> AWK-1137C 回 `0x0b`（=11）就被判非法，整条 0x16 应答被丢弃、固件列留空。

> AXOM/40404 设备的固件来自 TLV `0x36001000`（§4），不走本命令；4000/5800 无固件字段。

### 2.5 型号回退（名称 → 商品名）

`0x03` 无数据时，用名称推导：去掉尾部 `_<数字>`（`NP6450_0001` → `NP6450`），再映射：
`NP*` → `NPort *`；`MG-*` → `MGate *`；`EDS-`/`EOM-`/`IA-` 等原样；无法识别则返回原代码（不返回空）。
实测：`NP6450` → `NPort 6450`、`MG-MB3180` → `MGate MB3180`，与 MXConfig/DSU 一致。

超时 400 ms，失败则型号留空，不影响 IP 结果。

## 3. 协议 B：UDP 4000（EDS 交换机，✅ 实证）

### 3.1 请求（6 字节，广播）——命令字节必须是 `0x48`

```
48 00 00 06 26 27      ← 发现请求，设备应答
49 00 00 06 26 27      ← 伴随帧，设备不应答（官方也发，保留以保持逐字节兼容）
```
`[0]`=命令；`[2:4]`=0x0006 总长；`[4:6]`=会话标识（设备**原样回显**，不校验）。

> **⚠️ 2026-11-03 修正（关键）**：早期实现只发 `0x49`，导致**所有只应答 4000 的 EDS 交换机全部搜不到**
> ——`192.168.100.1`（EDS-510A-3SFP-2SSC）与 `192.168.100.2`（EOM-409-3SSC）就是这样漏掉的，
> 而 `.3/.4/.253` 因为同时应答 4800/40404 才没暴露问题。
>
> 实测对照（`_analysis/probe_4000_pair.py`，同一台 PC、同一时刻、只有命令字节不同）：
>
> | 发出的请求 | 应答设备数 |
> |---|---|
> | `49 00 00 06 7d48` | **0** |
> | `48 00 00 06 7d48` | **5** |
> | `49` + `48` | 5 |
> | `48` + 30 字节 MAC 列表（36 B） | **0** |
>
> 会话号任意：`0x2627` / `0x7D48` / `0x9A3C` 都能收到应答，且被原样回显。
> 带 MAC 列表的 36 字节变体是官方后续轮次用的，**本工具不要发**（实测 0 应答）。

### 3.2 应答（64 字节，✅ 实证）

```
c9 00 00 40 | 26 27 | 0f bf 1a 66 03 00 e4 05 | c0 a8 64 64 | 00 90 e8 00 00 32 | "EDS-408A-SS-SC-T" + 0
```
- `[0]`=0xC9（= 0x48 | 0x80）、`[2:4]`=总长（BE16，64）
- `[4:6]`=会话标识（回显）
- `[6:14]`=8 字节标识（序列号相关，忽略）
- `[14:18]`=**请求方 IPv4，不是设备地址**
- `[18:24]`=设备 MAC
- `[24:64]`=型号/名称 ASCII（40 字节，NUL 填充）

> **⚠️ `[14:18]` 是请求方地址（2026-11-03 修正）**：抓包里 5 台设备的应答在这一段**全部**是
> `c0a8 7f64` = `192.168.100.100`（那台 PC 自己），而设备真实地址只在 UDP **源地址**里。
> 早期实现按文档把 `[14:18]` 当设备 IP，会把每台 EDS 都标成 PC 的地址；EDSConfig 也是靠源地址给
> 行打标签的。设备地址在 178 字节详情应答的 `[76:80]`，但那是可选请求。

**解析规则**：`payload[0] == 0xC9` 且 `len >= 24` → IP=**UDP 源地址**（无源地址时才退回 `[14:18]`）、
MAC=`[18:24]`、型号=`[24:]` 去 NUL 去空白。

### 3.3 详情应答（178 字节，单播 `01 00 00 06 <seq>`，本工具暂未使用）

| 偏移 | 内容 | 实测（.1） |
|---|---|---|
| `[0]` | 0x81（= 0x01 \| 0x80） | — |
| `[2:4]` | 总长 0x00B2 = 178 | — |
| `[14:18]` | 请求方 IPv4 | `192.168.100.100` |
| `[24:64]` | 设备描述（40 B） | `Managed Redundant Switch 00003` |
| `[76:80]` | **设备 IPv4** | `192.168.100.1` |
| `[80:84]` | 子网掩码 | `255.255.255.0` |
| `[98:...]` | 位置 | `Switch Location` |

> 178 字节里**没有固件版本、没有序列号**（逐字节核对过 3 台）。所以只应答 4000 的交换机
> （`.1`/`.2`）固件列必然为空；`.253` 能显示 `V3.10 build 19121910` 是因为它**同时应答 4800** 的 `0x16`。

## 4. 协议 C：UDP 40404 AXOM（WIFI6 / AWK-1161，✅ 实证）

### 4.1 请求（40 字节，广播）——**有两种类型，必须都发**

```
偏移  长度  内容
0     4     "AXOM"
4     1     0x20            （= 总长 40 - 8）
5     3     00 00 00
8     4     00 08 01 07     类型 A：WIFI6 / AWK-1161 / EOM-106
            00 08 01 01     类型 B：EDS-G4012 等新交换机
12    4     0x18 (LE32)=24  （偏移 16 起的字节数）
16    4     00 00 00 01     （序号，回显）
20    4     0x10 (LE32)=16  （nonce 长度）
24    16    随机 nonce      （设备**原样回显**，用于配对）
```

> **⚠️ 两种类型必须都发（✅ 2026-11-03 实机验证）**
> 抓包 `mxconfigcs-g4000.pcapng` 显示 MXConfigCS 对同一台设备**先发 `…01` 再发 `…07`**；
> 而 EDS-G4012 **只应答 `…01`**。原样重放两组请求的结果（`_analysis/replay_g4000.py`）：
> `…01` → 2 次 136 B 应答，`…07` → 0 次应答，其余字节完全相同。
> WIFI6 那边（`mxconfigcs-wifi6.pcapng`）MXConfigCS 只发 `…07`，应答也是 132 B 的 `…07`。
> 因此工具对每张网卡**两种类型各发一份**（多 40 字节），回包按 (MAC, IP) 去重合并。

### 4.2 应答（WIFI6 132 字节 / EDS-G4012 136 字节，✅ 实证）

```
0    4   "AXOM"
4    1   0x7c (=132-8)       WIFI6；EDS-G4012 这里是 0x80 (=136-8)
8    4   00 08 01 07         （回显请求类型：WIFI6 为 07，G4012 为 01）
12   4   0x74 (=132-16)      实际是 LE32 的长度字段（G4012 为 0x78）
16   4   00 00 00 01        （回显序号）
20   4   0x10 (LE32)=16     （nonce 长度）
24   16  nonce（回显）
40   ..  TLV 序列（见下）
```

> 解析时**不要**按固定长度或 `[4]`/`[8:12]` 的取值做校验：G4012 的 `[4]=0x80`、
> 类型回显 `01`，而 WIFI6 是 `0x20`/`07`。只校验 `"AXOM"` 魔数与 TLV 结构即可。

**TLV 格式**：`type(BE32) | len(BE32) | value(len 字节)`，**每个 TLV 起点按 4 字节对齐**（value 长度非 4 的倍数时补 0 到对齐；实测 6 字节 MAC 后补 2 字节）。

| type | 含义 | 实测 |
|---|---|---|
| `0x34000001` | 主机名/名称（NUL 填充） | `"awk-1161c"`、`"EOM-106"` |
| `0x10000001` | 设备 IPv4（4 B） | `192.168.100.252` |
| `0x33000001` | 设备 MAC（6 B） | `50:0B:88:00:00:53` |
| `0x11000001` | 子网掩码（4 B） | `255.255.255.0` |
| `0x32000001` | 序列号（ASCII） | `"TBFGB1029561"` / `"MOXARDSAMPLE"` |
| **`0x36001000`** | **固件版本**：value 是 **纯 ASCII 文本**（末尾带 `\n`） | `V3.1.10 build 26102915\n` |
| `0x37000001` | 设备描述 | `"Managed Redundant Switch 00001"` |
| `0x38000001` | 位置 | `"Switch Location"` |
| `0x31000001` | 未知（4 B，EDS-G4012 为 `80 00 00 00`） | 勿使用 |
| `0x01000007` | 未知（4 B，值 1/2） | 勿使用 |
| `0x39000001` | 请求方 IP（4 B） | `192.168.100.100` |

> **固件解码要点（✅ 2026-11-02 实机验证，2 台 EOM-106）**：
> `0x36001000` 的 value 就是 **ASCII 原文**，形如 `56 33 2e 31 2e 31 30 20…` = `"V3.1.10 build 26102915\n"`。
> 处理方式：按文本解码 → `strip("\r\n \t ")` → 校验不含不可打印字符，否则按空处理。
> ⚠️ **不要**把它当 hex 编码再解一次（早期文档曾误判为 hex，是因为探测脚本把结尾 `\n` 当成不可打印
> 而回退打印了 hex，属于工具误读；若实现里保留 hex 兜底，必须先确认解码结果全为可打印字符才可采用）。

> 解析必须**按 TLV 遍历**，不要用固定偏移；未知 type 跳过。

## 5. 协议 D：UDP 5800 WSU（WIFI4 / AWK-1131A）

> 与 `2026-09-22-awk-config-tool` 已实现方案一致（`docs/DISCOVERY_PROTOCOL_FRAME.md`），本工具**复用同一字节布局**。

### 5.1 请求（68 字节）

```
[0]=00 01  [2]=00 01  [4:8]=BE32(68-36)=32  [8:20]=0
[20:26]=本网卡 MAC
[26:36]=0
[36:38]=00 01  [38:40]=BE16(68-40)=28  [40:42]=00 00  [42:44]=00 01
[44:46]=BE16(68-46)=22
[46:62]=本机 IP 字符串，16 B 定长左对齐 NUL 填充
[62:68]=本机监听端口字符串（"15802\0"）
```

发送：目的 `255.255.255.255:5800`，**每个网卡各一份**，报文内嵌该网卡 MAC/IP/端口。

### 5.2 应答（218 字节；**实测 AWK-1132C / AWK-1137C 为 234 字节**）

```
[0:2]=魔数：0x0DBD（AWK-1131A）/ 0x0DBF（AWK-1132C）/ 0x1DBF（AWK-1137C）  ← 见下方警告
[2:4]=0x0001
[4:8]=BE32(payload_len - 36)      ← 用来自校验，勿当常量
[20:26]=设备 MAC
[26:32]=请求方网卡 MAC（回显，可用于归属）
[46:58]=型号 ASCII（如 "AWK-1131A-EU" / "AWK-1137C-EU"，12 B 定长）
[79:95]=设备 IP 字符串
[95:113]=设备 MAC 字符串
[113:127]=子网掩码字符串
[177:193]=请求方 IP 字符串
```

> ⚠️ **魔数不是常量（2026-11-02 实机修正，两次）**：
> 第一轮：AWK-1131A 回 `0x0DBD`，**AWK-1132C 回 `0x0DBF`** —— 早期只认 `0x0DBD` 且要求长度恰为 218，
> 导致 AWK-1132C 应答整帧被丢、型号为空。
> 第二轮：**AWK-1137C 回 `0x1DBF`（高字节是 `0x1D`，不是 `0x0D`）** —— 只判断"高字节恒 `0x0D`"
> 又把 1137C 整帧丢弃（官方工具与旧版 WIFI4 工具均为 `MAGIC_SEEN_FIRST_BYTES=(0x0D,0x1D)`）。
> 判定应写成：**高字节 ∈ {`0x0D`,`0x1D`}、低字节 ∈ {`0xBD`,`0xBF`}**，并配合 `[2:4]==0x0001` 与
> `[4:8]==len-36`（不一致时走扫描兜底）做结构自校验；长度用 `len(payload)` 自适应（234 亦合法）。
> AWK-1132C / AWK-1137C 帧尾部比 218 版本多 16 字节（`…` 等常量域），固定偏移 46/79/95/113 不变。

**端口**：本工具优先绑定 `15802` 收应答（与官方一致）；若该端口已被其它程序占用（典型：官方 `Wireless Search Utility` 会绑 `0.0.0.0:15802`），
则退化为临时端口，并在报文 `[62:68]` 里**广告实际绑定端口**。

> ✅ **实测（2026-11-02，AWK-1132C）**：用随机本地端口 `62603` 发包并广告 `"62603"`，设备仍正常回包（234 B，型号 `AWK-1132C-US`）。
> 即**设备是按报文广告的端口回包的**，不必强占 15802。
> ⚠️ 检测占用必须用**通配地址探针**（`0.0.0.0:15802` + `SO_EXCLUSIVEADDRUSE`）：绑 `<网卡IP>:15802` 时，
> 即使别的进程已占 `0.0.0.0:15802`，Windows 也会让 bind 成功（设不设 `SO_REUSEADDR` 都一样），
> 于是回包被对方截走、本工具静默收不到——这正是"官方工具一开就搜不到 WIFI4 型号"的原因。

## 5.3 应答尾部的不透明块（**固件版本号就在这里**，2026-11-03 实验确证）

位置：`[193 : payload_len]`（218 版 = 25 B；234 版 = 41 B，其中前 28 B 有数据、后 13 B 补零）。

```
AWK-1131A (218B) [193:218] = 31 b7 ed e9 3d f9 33 b0 e2 ec 5c 89 f4 c3 49 80
                             2f 3a 1a d0 dd e0 31 59 e8
AWK-1137C (234B) [193:221] = 88 47 96 b9 c8 5c 80 95 ff dc 8c 5d 3a 22 83 e8
                             2b b8 0f 1f d0 7a 4e 68 39 62 72 30
```

**这是"加密的设备信息块"，不是签名/HMAC，也不是明文。** 官方 `Wireless Search Utility`
把整块解出来后显示为 `Firmware version` 列（格式 `<ver> Build <build>`，与 WSU 自身版本串
`2.0 Build 15021313` 同款）。

### 判定依据（**用官方 WSU 当解码器**做的黑盒实验，非推测）

方法：伪造一台 5800 设备（不同 MAC / IP），故意改块内字节，看 WSU 固件列怎么变。

| 实验 | 改动 | WSU 显示 |
|---|---|---|
| 基线 | 原样回放 1131A 的块 | `1.27 Build 25092317` |
| **换块** | 把 **1137C 的块**塞进 1131A 帧（MAC/IP 都改成假的） | **`1.11 Build 25092317`** |
| 破坏 | 块内任意 1 个字节改 0 | 整串乱码（不是缺字/错字） |
| 块外 | 改型号字符、改 `[8:10]`、改 `127–176` 保留区 | 仍 `1.27 Build 25092317` |

结论：**固件版本完全由这 25 B 决定，且与 MAC / IP / 型号 / 帧内其它字段无关**（块是自包含的）。

### 为什么不能当字段读

- 不是 ASCII：没有 `1.27` / `25092317` / `0x1B` 任何形态（逐帧逐字节核过 24 帧）；
- 不是定长异或 / 单字节异或 / 周期密钥（1–12）加减 / 位反转 / 半字节交换 / zlib / gzip / raw deflate；
- 不是 AWK `$AE$` 那套 AES-256-CBC（用 `AWK加密算法` 里的 KEY/IV 对全帧所有 16 B 对齐位置都试过）；
- **任何 1 字节改动导致整串乱码** ⇒ 解密密钥/派生种子与整块内容绑定（自校验式混淆），
  不是"字段 + 校验"结构，无法按偏移直接取值；
- 同一设备 38 帧内该块**逐字节恒定**（与帧内计数器无关）。

> ⚠️ 因此：**不要**再尝试用 `[193:...]` 做任何"按偏移取版本"的解析，也不要把末尾
> `31 59`（ASCII `1Y`）当成版本号——它只是这块密文的一部分。
> **✅ 2026-11-03 已破解并实现**，见 §5.3.1 与 `src/internal/discovery/firmware_wsu.go`
> （`DecodeWSUFirmware`）。另一条路仍有效：AWK-1137C 这类走 4800 `0x16` 的型号直接用设备自答值。

## 7. 收发与网络架构（已实测验证）

1. **每网卡独立 socket**：`bind(网卡 IPv4, 0)`（5800 协议用 `bind(网卡 IPv4, 15802)`）。
2. 开启 `SO_BROADCAST`、`SO_REUSEADDR`。
3. 每张网卡对每个协议端口**各发 2 个目标**：
   - 受限广播 `255.255.255.255`
   - 子网定向广播 `(ip & mask) | ~mask`
4. **收包在同一 socket 上完成**。已用 `_analysis/bcast_probe.py` 实测：Windows 下绑定具体网卡 IP 的 socket **能收到**发往 `255.255.255.255:该端口` 的广播回包（官方 4800/4000 应答正是广播回包），无需 0.0.0.0 监听。
5. 网卡枚举：`net.Interfaces()`，过滤 `FlagUp`、非 loopback、IPv4 地址，跳过 169.254.x.x（可选）。
6. **跨网段**：受限广播只在二层内传播，因此设备 IP 与本机不同网段也能收到——这是官方工具的原理，也是本工具满足需求的依据。**不做**路由跨三层的承诺。
7. 轮次：`3 轮 × 400 ms`，轮间重发；总时长约 1.5 s（可配置）。
8. 端口占用（官方工具同时运行）时记录警告，继续其他端口。

## 8. 去重与"同 IP 多设备"规则（关键需求）

> ⚠️ **v1.1 已修订**：去重键由「MAC」改为「(MAC, IP)」。原规则会把「一台设备有多个 IP」合并成一行而丢掉地址，
> 与「列出所有 IP」的目标冲突。当前实现与验收以此节为准。

- **行身份 = (MAC, IPv4)**：同一个 `(MAC, IP)` 从多协议/多网卡被发现 → 合并为一行，
  协议取优先级最高的（4800 > 4000 > 40404 > 5800 > 其他），「设备信息来源网卡」列合并去重。
- **绝不按 IP 去重**：同一 IP 对应多个 MAC（多台设备撞 IP）→ **每台一行**，全部列出。
- **同一 MAC 的不同 IP → 各自成行**（设备多归属地址时每个地址都要可见）。
- MAC 未知时（仅兜底协议收到 IP），行身份退化为 `(IP, 协议)`。
- 状态栏的「搜索到 N 台设备」按 **MAC 去重的台数**统计，不是行数；存在撞 IP 时追加「（M 台设备 IP 重复）」。
- 实测样例：`192.168.100.253` 与 `192.168.100.254` 在同一抓包中同时存在（同型号不同设备），必须两行都列出。

## 9. 型号与区域（ubus，✅ 2026-11-02 实机）

**发现报文里没有型号后缀**：AXOM 40404 的 15 个 TLV（序列号/MAC/主机名/类别码/IP/掩码/固件/描述/位置/…）都不含
`UN`/`US`；主机名是用户自定义（如 `awk-1161c`），**不能当型号**。

设备的 web 平台（ubus，JSON-RPC 2.0）提供**免登录只读**接口：

```
POST https://<设备>/ubus
{"jsonrpc":"2.0","id":1,"method":"call",
 "params":["00000000000000000000000000000000","moxa.web.ui","contents_for_login",{}]}
→ {"result":[0,{"login_msg":"","login_fail_msg":"Failed to login","model":"AWK-1161C-UN"}]}
```

- 匿名会话 id = 32 个 `0`；自签名证书 ⇒ 跳过 TLS 校验。
- 交叉验证：`moxa.default` / `get_unus` → `{"code":0,"unus":"UN"}`。
- `system board` / `system info` 返回 `Access denied`，不可用。
- 无 ubus 的老设备（如 EDS-405A）会 302 到 `/auth/auth.asp`，按失败处理。

### 归属：撞 IP 时绝不能按 IP 猜

`192.168.100.253` 上可同时有 4 台设备。HTTPS 按 IP 走只会到 ARP 解析到的那台，而 ARP 在它们之间**反复变化**
（实测同一轮里 `.253` 可能指向 AWK-1132C 或 EDS-408A）。

**解法：IPv6 链路本地地址由 MAC 经 EUI-64 唯一派生**，可精确定位到某一台：

| MAC | 链路本地 | 结果 |
|---|---|---|
| `50:0B:88:00:00:1A` | `fe80::520b:88ff:fe00:1a` | `AWK-1161C-UN` ✅ |
| `50:0B:88:00:00:2C` | `fe80::520b:88ff:fe00:2c` | 302，无 ubus |
| `00:90:E8:…`（未开 IPv6） | — | 超时 → 回落 IPv4 |

EUI-64：MAC 首字节 `^0x02`，第 3、4 字节间插 `ff:fe`，前缀 `fe80::`；拨号目标形如 `[fe80::…%<接口索引>]:443`。

**查询顺序**：先 IPv6 链路本地（身份由 EUI-64↔MAC 保证，无需 ARP 校验）→ 失败再走 IPv4 + **ARP 归属校验**
（该 IP 的 ARP MAC 必须等于设备 MAC 才采用）。两条都失败就保留主机名兜底，绝不错误归属。

**区域**：只在**设备真实回答的型号**上解析尾部 `-UN`/`-US` 等（取最后一个 `-` 后的 2–3 字母）。
主机名兜底不解析——否则 `EDS-408A-SS-SC` 会误判出 `SC`（那是单模光纤接口，不是区域）。
